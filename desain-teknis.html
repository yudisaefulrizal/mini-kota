Lima tahap mengikuti pola umum pemantauan IoT. Setiap sensor mengirim hasil deteksi (bukan video) sebagai event, Kafka menampung dan membagi event per topik, lalu Spark menghitung kondisi tiap window dan meneruskan hasilnya.

Jaringan antar perangkat

Perangkat yang punya listrik memakai kabel atau serat optik karena paling stabil. Radio hanya dipakai untuk sensor berbaterai.

1 · Sensor kota

Jumlah perangkat mengikuti perangkat yang terpasang di peta default (Mini Kota lengkap), sama dengan panel Data Center; peta lain dari editor menghasilkan jumlahnya sendiri. Privasi: sistem hanya memakai data agregat (jumlah kendaraan per pendekat, isi tempat sampah). Tidak ada pembacaan plat, identitas kendaraan, atau pelacakan perjalanan, sehingga tidak ada pengarahan rute per kendaraan. Kamera menjalankan analitik di perangkat dan hanya mengirim metadata: jumlah kendaraan, panjang antrean, dan arah gerak.

2 · Gateway edge

Satu gateway melayani sekelompok sensor di satu simpang atau kawasan. Gateway memberi cap waktu, memvalidasi format, menyangga pesan saat jaringan putus, lalu mengirim ke Kafka sebagai producer. Kunci pesan adalah node_id simpang atau lot_id kawasan, sehingga semua event satu lokasi masuk ke partisi yang sama dan urutannya terjaga.

{
  "sensor_id": "Q-simpang07-utara",
  "type": "queue",
  "node_id": "simpang07",
  "timestamp": "2026-10-18T07:42:15+07:00",
  "vehicles_in_zone": 14,
  "stopped": 11,
  "queue_m": 62.5
}

3 · Apache Kafka

Topik dipisah menurut jenis dan frekuensi data agar retensi dan jumlah konsumen dapat diatur sendiri-sendiri.

TopikKunci partisiIsi

Replikasi 2 salinan, sesuai asumsi penyimpanan pada panel Data Center. Retensi Kafka cukup beberapa hari; arsip panjang dipindahkan ke data lake.

4 · Spark Structured Streaming

Spark membaca kedua topik, mengurai JSON, lalu menghitung kondisi per lokasi dalam window 1 menit. Watermark 30 detik menerima event yang terlambat sedikit, dan checkpoint menyimpan posisi baca agar tidak ada event yang hilang atau dihitung ganda saat job dimulai ulang.

  • Read stream dari Kafka
  • Parse & filter event rusak atau sensor tak dikenal
  • Window 1 menit per node_id / lot_id
  • Agregasi rata-rata antrean, maksimum antrean, total arus
  • Deteksi kondisi dengan aturan di bawah
  • Stateful + checkpoint status sensor dan tempat sampah

5 · Output & sink

Lampu lalu lintas adaptif

Pengendali simpang menerima panjang antrean per arah dan memakai aturan yang sama dengan kota cerdas di simulasi: hijau minimal 10 detik, maksimal dua kali hijau pengaturan (batas 90 detik), kuning 3 detik, merah bersama 1 detik. Lihat jalur cepat.

Dashboard real-time

Status tiap simpang (lancar, padat, macet), isi tempat sampah dan panggilan truk, serta arus per pendekat. Bentuknya mirip panel perbandingan di simulasi.

Contoh kejadian yang tercatat

Spark mencatat kejadian di PostgreSQL untuk ditampilkan di dashboard.

{
  "node_id": "simpang07",
  "window": "07:42–07:43",
  "event": "QUEUE_CONGESTED",
  "risk": "HIGH",
  "details": { "max_queue_m": 92.0, "avg_stopped": 13.4 }
}

Data lake

Event mentah dan hasil window disimpan sebagai Parquet di HDFS atau S3, dipartisi per tanggal. Data ini dipakai untuk analisis jam sibuk, evaluasi pengaturan lampu, dan perencanaan rute truk.

Anggaran latensi kontrol lampu

Perkiraan untuk jaringan kabel lokal di simpang. Angka ini target rancangan, bukan hasil pengukuran.

TahapPerkiraan
Analitik di kamera (deteksi per frame)50–150 ms
Menunggu jadwal kirim (interval 250 ms)0–250 ms
MQTT kamera → gateway (kabel lokal)< 10 ms
Keputusan lampu di gateway< 5 ms
Perintah gateway → pengendali (NTCIP, Ethernet lokal)< 50 ms
Total terburuk± 0,5 detik

Setengah detik sudah cukup karena lampu sendiri berubah dalam hitungan detik: hijau minimal 10 detik, lalu kuning 3 detik dan merah bersama 1 detik sebelum arah lain hijau. Di simulasi, lampu adaptif dievaluasi 4 kali per detik, sehingga kamera mengirim ke gateway setiap 250 ms. Ke data center, gateway hanya meneruskan ringkasan per 1 detik; angka inilah yang dipakai pada hitungan kapasitas.

  • Kafka dan Spark tidak berada di jalur kontrol lampu. Window 1 menit dan jaringan ke data center terlalu lambat dan tidak pasti untuk lampu.
  • Jaringan kota juga tidak dipakai untuk kontrol lampu. Jika putus, lampu tetap bekerja; hanya dashboard dan arsip yang tertunda.
  • Pengendali memasang watchdog: tanpa data dari gateway selama 2 detik, simpang kembali ke lampu tetap seperti kota biasa.
  • Pemantau konflik di kabinet tetap menjadi pengaman terakhir, terlepas dari software gateway.

Kebutuhannya kecil, 2 vCPU dan 6 GB RAM, sehingga Kafka dan Spark untuk satu kota ini cukup berjalan di klaster kecil di gedung data center. Penambahan worker

Worker adalah node komputasi yang menjalankan executor Spark. Broker Kafka ditambah terpisah, karena broker menanggung penyimpanan dan throughput pesan, bukan perhitungan.

Kapan worker ditambah

  • Consumer lag Kafka terus naik selama lebih dari 5 menit. Artinya Spark membaca lebih lambat daripada sensor mengirim.
  • Durasi micro-batch lebih lama dari interval trigger, sehingga batch berikutnya selalu terlambat.
  • CPU worker di atas 60%, sama dengan target utilisasi pada rumus kapasitas, atau RAM hampir penuh.

Berapa worker yang dibutuhkan

Jumlah node mengikuti rumus panel Data Center: node aktif = maksimum dari 1, ⌈vCPU ÷ 8⌉, dan ⌈RAM ÷ 16 GB⌉, lalu ditambah satu cadangan (N+1). Bebannya hanya pesan sensor dan evaluasi lampu, sehingga jumlah sensor yang menentukan; jumlah kendaraan tidak, karena tidak ada data per kendaraan.

Penyimpanan tumbuh lebih cepat daripada komputasi, sehingga untuk kota besar arsip lebih baik dipindahkan ke data lake dengan retensi lebih pendek di Kafka.

Langkah menambah worker

  1. Daftarkan node baru ke pengelola klaster (Kubernetes, YARN, atau Spark standalone).
  2. Naikkan jumlah executor job Spark, misalnya satu executor per node, lalu mulai ulang job. Checkpoint menyimpan offset Kafka terakhir, jadi job melanjutkan dari posisi tersebut tanpa kehilangan atau menggandakan event.
  3. Pastikan jumlah partisi cukup. Satu partisi Kafka hanya dibaca oleh satu task Spark pada satu waktu, sehingga worker di atas jumlah partisi akan menganggur. Buat traffic_events dengan cadangan partisi sejak awal, misalnya 12. Menambah partisi belakangan mengubah pemetaan kunci ke partisi, sehingga urutan event per simpang terganggu sesaat.
  4. Periksa lagi consumer lag dan durasi batch. Worker sudah cukup jika keduanya stabil.

Saat beban turun, worker dapat dikurangi dengan langkah yang sama, tetapi node cadangan tetap dipertahankan. Penambahan atau pengurangan worker tidak menghentikan lampu lalu lintas, karena keputusan lampu memakai jalur cepat di simpang.

Batas rancangan

Halaman ini adalah usulan arsitektur, bukan sistem yang sudah dibangun. Simulasi tidak menjalankan Kafka, Spark, gateway, atau kamera. Video mentah, inferensi kamera, GPU, listrik, dan pendinginan tidak termasuk dalam estimasi. Ambang deteksi dan pembagian partisi perlu diuji dengan data lapangan.
