Arsitektur aliran data

Tujuh tahap. Setiap sensor mengirim hasil deteksi (bukan video) sebagai event, Kafka menampung dan membagi event per topik, Spark menghitung kondisi tiap window, hasilnya disimpan dan ditampilkan, lalu model belajar dari riwayatnya dan parameternya kembali ke simpang.

  1. 1Sensor kotaKamera detektor antrean · ultrasonik
  2. 2Gateway edgeJalur cepat lampu · producer Kafka
  3. 3Apache Kafkatraffic · waste
  4. 4Spark StreamingWindow, agregasi, deteksi kondisi
  5. 5PenyimpananClickHouse · MinIO + Iceberg
  6. 6OutputLampu adaptif · Grafana
  7. 7PembelajaranAirflow + Spark MLlib → kembali ke gateway

Pola Kappa: semua data diperlakukan sebagai stream lewat satu jalur (Kafka → Spark). Tidak ada jalur batch terpisah seperti pada arsitektur Lambda; data lama dihitung ulang dengan memutar kembali Kafka atau membaca tabel Iceberg, dengan kode yang sama. Satu jalur berarti satu logika, lebih mudah dijaga konsistensinya.

Saat ada gangguan: keputusan lampu tidak bergantung pada data center. Jika jaringan kota putus, simpang tetap diatur gateway dan pengendali; gateway menyangga event lalu mengirimnya saat tersambung lagi. Jalur ke data center mengutamakan ketersediaan (sensor tetap menulis), sedangkan dashboard boleh tertinggal sesaat.

Jaringan antar perangkat

Perangkat yang punya listrik memakai kabel atau serat optik karena paling stabil. Radio hanya dipakai untuk sensor berbaterai.

1 · Sensor & aturan pemasangan

Jumlah perangkat tidak ditetapkan di rancangan; yang ditetapkan adalah aturan pemasangannya, sehingga berlaku untuk kota sebesar apa pun. Jumlah untuk peta tertentu dihitung dari aturan ini (panel Data Center). Sistem hanya memakai data agregat: kamera menjalankan analitik di perangkat dan hanya mengirim angka (jumlah kendaraan, kendaraan berhenti, panjang antrean). Tidak ada pembacaan plat atau pelacakan kendaraan.

2 · Gateway edge

Satu gateway melayani sekelompok sensor di satu simpang atau kawasan. Gateway memberi cap waktu, memvalidasi format, menyangga pesan saat jaringan putus, lalu mengirim ke Kafka sebagai producer. Kunci pesan adalah node_id simpang atau lot_id kawasan, sehingga semua event satu lokasi masuk ke partisi yang sama dan urutannya terjaga.

{
  "sensor_id": "Q-simpang07-utara",
  "type": "queue",
  "node_id": "simpang07",
  "timestamp": "2026-10-18T07:42:15+07:00",
  "vehicles_in_zone": 14,
  "stopped": 11,
  "queue_m": 62.5
}

3 · Apache Kafka

Topik dipisah menurut jenis dan frekuensi data agar retensi dan jumlah konsumen dapat diatur sendiri-sendiri.

TopikKunci partisiIsi
traffic_eventsnode_id simpang / ruasAntrean dan arus per arah simpang · 1 pesan/detik per kamera
waste_eventslot_id kawasanPersentase isi tempat sampah

Minimal 3 broker (kuorum KRaft), replikasi 2, retensi 3 hari; arsip panjang ada di Iceberg. Jumlah partisi traffic_events dibuat dengan cadangan sejak awal (minimal 12, kira-kira 1 per 1.000 pesan/detik), karena menambah partisi belakangan mengubah pemetaan kunci ke partisi.

4 · Spark Structured Streaming

Spark membaca kedua topik, mengurai JSON, lalu menghitung kondisi per lokasi dalam window 1 menit. Watermark 30 detik menerima event yang terlambat sedikit, dan checkpoint menyimpan posisi baca agar tidak ada event yang hilang atau dihitung ganda saat job dimulai ulang.

  • Read stream dari Kafka
  • Parse & filter event rusak atau sensor tak dikenal
  • Window 1 menit per node_id / lot_id
  • Agregasi rata-rata antrean, maksimum antrean, total arus
  • Deteksi kondisi dengan aturan di bawah
  • Stateful + checkpoint status sensor dan tempat sampah

5 · Penyimpanan

Dua lapis, satu peran untuk masing-masing: data panas yang cepat di-query untuk dashboard, dan arsip besar yang murah untuk analisis jangka panjang dan pelatihan model.

LapisToolsIsiBentuk
PanasClickHouseHasil window per menit dan kejadian, ±90 hariTabel MergeTree dipartisi per hari, diurutkan per wilayah H3, simpang, dan waktu; ringkasan otomatis menit → jam → hari; data lewat batas dipindahkan ke Iceberg
ArsipMinIO + Apache IcebergEvent mentah dan hasil, data latih, versi model, checkpoint SparkTabel Iceberg (Parquet) dipartisi per tanggal dan wilayah H3; transaksi ACID; time travel untuk audit keputusan lampu; MinIO dengan erasure coding, minimal 4 node

H3 (indeks heksagonal) dipakai sebagai kunci wilayah: setiap simpang dan tempat sampah diberi sel H3, sehingga data antar kota dan provinsi bisa disatukan, dipartisi, dan diringkas dengan ukuran sel yang seragam.

6 · Output

Lampu lalu lintas adaptif

Pengendali simpang menerima panjang antrean per arah dan memakai aturan yang sama dengan kota cerdas di simulasi: hijau minimal 10 detik, maksimal dua kali hijau pengaturan (batas 90 detik), kuning 3 detik, merah bersama 1 detik. Lihat jalur cepat.

Dashboard (Grafana)

Grafana membaca ClickHouse: status tiap simpang (lancar, padat, macet), isi tempat sampah dan panggilan truk, arus per arah, dan ringkasan per wilayah H3. Metrik sistem (consumer lag, CPU, durasi batch) dari Prometheus tampil di dashboard yang sama, lengkap dengan peringatan.

Contoh kejadian yang tercatat

Spark mencatat kejadian di ClickHouse untuk ditampilkan di Grafana.

{
  "node_id": "simpang07",
  "window": "07:42–07:43",
  "event": "QUEUE_CONGESTED",
  "risk": "HIGH",
  "details": { "max_queue_m": 92.0, "avg_stopped": 13.4 }
}

7 · Pembelajaran & alur balik

Model belajar dari data sensor yang sudah ada, tanpa data tambahan. Apache Airflow menjadwalkan satu DAG setiap malam; pekerjaan beratnya dijalankan di Spark (MLlib).

  1. Kualitas data: kelengkapan per sensor dan nilai yang mustahil.
  2. Ringkasan & perawatan: ringkasan harian di ClickHouse, pemadatan file kecil dan pembersihan snapshot lama di Iceberg.
  3. Latih ulang: enam model dari histori di Iceberg (rentang data latih bisa dibatasi).
  4. Kirim: parameter baru langsung dikirim ke gateway lewat jaringan kota (MQTT TLS); gateway memeriksa batas aman sebelum memakainya.

Setiap baris histori diberi waktu, label jam, tanggal Masehi dan Hijriah, dan versi tiap model yang sedang dipakai, supaya pola harian, mingguan, dan bulan Hijriah (misalnya Ramadan) bisa dipelajari.

ModelMetodeHasil yang dikirim balik

Prediksi isi tempat sampahRegresi linearLaju isi per tempat sampah, lama truk tiba
Prediksi waktu tempuh antar simpangKorelasi silangWaktu tempuh dan bagian rombongan per pasangan simpang
Optimasi durasi hijau per faseBayesian optimizationBagian hijau per fase dan pengali hijau rencana, sesuai jam dan tanggal
Optimasi penahanan hijauBayesian optimizationBerapa detik ke depan lampu hilir menahan hijau untuk rombongan

Alur balik: Airflow → jaringan kota → gateway → pengendali. Pengaman konflik di kabinet pengendali tetap menjadi lapisan terakhir, apa pun parameter yang diterima. Siklus yang sama dijalankan di tab Analisis aplikasi, memakai histori kota cerdas yang sedang berjalan, disimpan di browser.

Latensi & jalur cepat lampu lalu lintas

Tidak semua data perlu secepat yang sama. Rancangan ini membagi latensi menjadi empat tingkat, dan hanya tingkat yang tidak kritis yang melewati jaringan kota, Kafka, dan Spark.

Anggaran latensi kontrol lampu

Perkiraan untuk jaringan kabel lokal di simpang. Angka ini target rancangan, bukan hasil pengukuran.

TahapPerkiraan
Analitik di kamera (deteksi per frame)50–150 ms
Menunggu jadwal kirim (interval 250 ms)0–250 ms
MQTT kamera → gateway (kabel lokal)< 10 ms
Keputusan lampu di gateway< 5 ms
Perintah gateway → pengendali (NTCIP, Ethernet lokal)< 50 ms
Total terburuk± 0,5 detik

Setengah detik sudah cukup karena lampu sendiri berubah dalam hitungan detik: hijau minimal 10 detik, lalu kuning 3 detik dan merah bersama 1 detik sebelum arah lain hijau. Di simulasi, lampu adaptif dievaluasi 4 kali per detik, sehingga kamera mengirim ke gateway setiap 250 ms. Ke data center, gateway hanya meneruskan ringkasan per 1 detik; angka inilah yang dipakai pada hitungan kapasitas.

  • Kafka dan Spark tidak berada di jalur kontrol lampu. Window 1 menit dan jaringan ke data center terlalu lambat dan tidak pasti untuk lampu.
  • Jaringan kota juga tidak dipakai untuk kontrol lampu. Jika putus, lampu tetap bekerja; hanya dashboard dan arsip yang tertunda.
  • Pengendali memasang watchdog: tanpa data dari gateway selama 2 detik, simpang kembali ke lampu tetap seperti kota biasa.
  • Pemantau konflik di kabinet tetap menjadi pengaman terakhir, terlepas dari software gateway.

Cara membesar

Setiap tools membesar sendiri-sendiri, mengikuti bebannya. Jumlah node dan penyimpanan untuk peta yang sedang dipakai dihitung di panel Data Center (tab Perangkat) dengan aturan di bawah. Semua layanan dijalankan di Kubernetes, sehingga node baru cukup didaftarkan ke klaster.

ToolsBertambah karenaCara menambah
KafkaPesan per detik dan penyimpanan 3 hariTambah broker, pindahkan sebagian partisi; partisi dibuat berlebih sejak awal
SparkConsumer lag dan beban CPUTambah worker (otomatis dari consumer lag, misalnya dengan KEDA); paling banyak satu task per partisi
ClickHouseBaris per hari dan masa simpanTambah shard per kelompok wilayah H3, masing-masing dengan 1 replika
MinIO + IcebergPenyimpanan arsipTambah kelompok node MinIO (server pool); tabel Iceberg tidak perlu diubah
GatewaySimpang dan kawasan baruDipasang di lapangan mengikuti aturan pemasangan; tidak mengubah data center

Kota baru bergabung sebagai wilayah H3 baru: gatewaynya menulis ke topik yang sama dengan kunci simpangnya sendiri, sehingga data center tidak perlu dirancang ulang.

Kapan worker Spark ditambah

  • Consumer lag Kafka terus naik selama lebih dari 5 menit. Artinya Spark membaca lebih lambat daripada sensor mengirim.
  • Durasi micro-batch lebih lama dari interval trigger, sehingga batch berikutnya selalu terlambat.
  • CPU worker di atas 60%, sama dengan target utilisasi pada rumus kapasitas, atau RAM hampir penuh.

Langkah menambah worker Spark

  1. Daftarkan node baru ke pengelola klaster (Kubernetes, YARN, atau Spark standalone).
  2. Naikkan jumlah executor job Spark, misalnya satu executor per node, lalu mulai ulang job. Checkpoint menyimpan offset Kafka terakhir, jadi job melanjutkan dari posisi tersebut tanpa kehilangan atau menggandakan event.
  3. Pastikan jumlah partisi cukup. Satu partisi Kafka hanya dibaca oleh satu task Spark pada satu waktu, sehingga worker di atas jumlah partisi akan menganggur. Buat traffic_events dengan cadangan partisi sejak awal, misalnya 12. Menambah partisi belakangan mengubah pemetaan kunci ke partisi, sehingga urutan event per simpang terganggu sesaat.
  4. Periksa lagi consumer lag dan durasi batch. Worker sudah cukup jika keduanya stabil.

Saat beban turun, worker dapat dikurangi dengan langkah yang sama, tetapi node cadangan tetap dipertahankan. Penambahan atau pengurangan worker tidak menghentikan lampu lalu lintas, karena keputusan lampu memakai jalur cepat di simpang.

Batas rancangan

Halaman ini adalah usulan arsitektur, bukan sistem yang sudah dibangun. Simulasi tidak menjalankan Kafka, Spark, ClickHouse, MinIO, Airflow, gateway, atau kamera; siklus belajar di tab Analisis memakai histori sensor kota cerdas simulasi dengan langkah yang sama, dijalankan di browser. Video mentah, inferensi kamera, GPU, listrik, dan pendinginan tidak termasuk dalam estimasi. Ambang deteksi dan pembagian partisi perlu diuji dengan data lapangan.
